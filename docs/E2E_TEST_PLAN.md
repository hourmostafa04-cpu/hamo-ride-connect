# E2E Test Plan — Hamoula (شاحن + سائق)

## الهدف
التحقق من تدفق كامل من التسجيل إلى التقييم، مع التأكد أن البيانات تبقى محفوظة بعد إغلاق وإعادة فتح التطبيق.

## المتطلبات قبل الاختبار
1. Supabase متصل وصالح.
2. جداول Phase 1 مطبقة (أو على الأقل الأساسية المطلوبة للمسار المختبر).
3. حسابان مختلفان:
   - حساب شاحن (shipper)
   - حساب سائق (driver)
4. تفعيل الإشعارات/الموقع عند الحاجة.

## سيناريو 1: تسجيل حساب الشاحن
1. افتح التطبيق.
2. اختر دور الشاحن.
3. أدخل رقم هاتف صالح.
4. أدخل OTP صحيح.
5. أكمل بيانات الحساب واحفظ.
6. تحقق أن الحساب محفوظ في `app_users`.

**Expected:** دخول ناجح + ظهور لوحة الشاحن.

## سيناريو 2: تسجيل حساب السائق
1. سجّل خروج من حساب الشاحن.
2. اختر دور السائق.
3. أدخل رقم هاتف مختلف.
4. أدخل OTP صحيح.
5. أكمل بيانات الشاحنة (النوع/السعة/اللوحة).
6. تحقق من حفظ بيانات السائق في `app_users`.

**Expected:** دخول ناجح + ظهور لوحة السائق.

## سيناريو 3: نشر طلب (شاحن)
1. ادخل بحساب الشاحن.
2. أنشئ طلب جديد (pickup/destination/cargo/truck/price).
3. انشر الطلب.
4. راقب جدول `loads`.

**Expected:** إنشاء load جديد بحالة `open` و`trip_status=searching` و`user_id` صحيح.

## سيناريو 4: تقديم عرض (سائق)
1. ادخل بحساب السائق.
2. افتح نفس الطلب.
3. أرسل عرض سعر.
4. راقب جدول `bids`.

**Expected:** إنشاء bid جديد بحالة `pending` مع `user_id` السائق.

## سيناريو 5: قبول/رفض العرض (شاحن)
1. ارجع لحساب الشاحن.
2. افتح "طلباتي".
3. اقبل عرضاً واحداً.
4. (اختياري) ارفض عرضاً آخر.

**Expected:**
- العرض المقبول => `accepted`
- باقي عروض نفس الطلب => `declined`
- الطلب => `status=assigned`, `trip_status=matched`, `accepted_offer` معبأ.

## سيناريو 6: تتبع الرحلة وتحديث الحالة
1. بحساب السائق، افتح الرحلة المقبولة.
2. بدّل الحالة بالترتيب: `enroute` ثم `loaded` ثم `delivered`.

**Expected:** الانتقالات مقبولة فقط بالترتيب عبر RPC `set_trip_status`، وأي انتقال غير صالح مرفوض.

## سيناريو 7: الشات/الصوت
1. افتح محادثة نفس الطلب.
2. أرسل رسالة نصية.
3. أرسل رسالة صوتية (إذا مفعلة).

**Expected:**
- الرسائل تظهر للطرفين فقط.
- الملفات الصوتية (إن وجدت) ترفع إلى bucket `chat-voice`.

## سيناريو 8: التقييم بعد التسليم
1. بعد `delivered`، ادخل صفحة التقييم.
2. قيّم الطرف الآخر.
3. حاول تقييم نفس الرحلة مرة ثانية.

**Expected:**
- أول تقييم ينجح في `trip_ratings`.
- التقييم الثاني مرفوض (unique constraint).

## سيناريو 9: استمرارية البيانات بعد إغلاق التطبيق
1. أغلق التطبيق بالكامل.
2. أعد فتحه وسجّل الدخول بنفس الحسابات.
3. راجع: الطلبات، العروض، حالة الرحلة، التقييم.

**Expected:** البيانات تبقى محفوظة ومتسقة (لا فقدان بيانات منشورة).

## سيناريو 10: التحقق من الصلاحيات
1. جرّب الوصول لبيانات رحلة غير مرتبطة بالمستخدم.
2. جرّب تعديل مباشر غير مسموح (مثلاً تحديثات حساسة خارج RPC).

**Expected:** رفض عبر RLS/صلاحيات Supabase.
