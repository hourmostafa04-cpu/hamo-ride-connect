# حزمة تنفيذ المرحلة 1 — مشروع حمولة (بدون تطبيق مباشر)

هذه الحزمة تُجهّز التنفيذ على شكل دفعات صغيرة وآمنة، **بدون أي تطبيق تلقائي**.
الهدف هو إكمال المشروع الحالي كما هو، مع أقل إعادة شغل ممكنة.

## محتويات الحزمة

1. `backup_instructions.md`
   - خطوات النسخ الاحتياطي الكامل (Schema + Data) والتحقق من صحته قبل أي تنفيذ.

2. `batch1_columns.sql`
   - إضافة أعمدة الملكية `user_id` للجداول الأساسية الحالية + الفهارس.
   - بدون حذف أي عمود قديم.

3. `batch2_tables.sql`
   - إنشاء الجداول الناقصة:
     - `chat_messages`
     - `push_subscriptions`
     - `trip_ratings`
   - مع الفهارس والتريغرز اللازمة.

4. `batch3_functions.sql`
   - إنشاء/تحديث الدوال المساعدة + RPC:
     - `owns_load`, `has_bid_on_load`, `is_chat_party`, `can_access_chat_load`, `current_user_phone_key`
     - `set_trip_status`, `update_own_load`, `update_own_bid`, `respond_to_bid`
   - مع صلاحيات `EXECUTE` المقيّدة.

5. `batch4_rls.sql`
   - تطبيق سياسات RLS آمنة لكل الجداول المستهدفة.
   - تعطيل/إسقاط السياسات المفتوحة القديمة.
   - سياسات آمنة لـ `storage.objects` الخاصة بـ `chat-voice`.

6. `verify_after_each_batch.sql`
   - استعلامات تحقق بعد كل دفعة (أعمدة، جداول، دوال، سياسات، صلاحيات).

## ترتيب التنفيذ المقترح (إجباري)

> **لا تتجاوز ترتيب الدفعات**، ولا تنفّذ الدفعة التالية قبل نجاح التحقق من الحالية.

1. نفّذ `backup_instructions.md` بالكامل.
2. نفّذ `batch1_columns.sql`.
3. نفّذ قسم التحقق الخاص بالدفعة 1 من `verify_after_each_batch.sql`.
4. نفّذ `batch2_tables.sql`.
5. نفّذ قسم التحقق الخاص بالدفعة 2.
6. نفّذ `batch3_functions.sql`.
7. نفّذ قسم التحقق الخاص بالدفعة 3.
8. نفّذ `batch4_rls.sql`.
9. نفّذ قسم التحقق الخاص بالدفعة 4.

---

## قواعد السلامة أثناء التنفيذ

- لا حذف لأي عمود قديم.
- لا تعديل للتصميم أو الكود العامل.
- أي خطأ في دفعة = توقّف فوري.
- لا ترقيع عشوائي بين الدفعات.
- كل دفعة يجب أن تنتهي بتحقق ناجح موثّق.

## ملاحظات Rollback عند فشل دفعة

### مبدأ عام
لو فشلت دفعة ولم يُحل السبب بسرعة:
1. أوقف التنفيذ.
2. لا تنتقل للدفعة التالية.
3. ارجع لنسخة Backup المؤكدة.

### حالات عملية
- **فشل في Batch 1 (أعمدة/فهارس):**
  - راجع تعارض أسماء الأعمدة والفهارس.
  - إن وُجدت حالة قاعدة غير متوقعة، الأفضل الاسترجاع ثم إعادة التنفيذ بخطة مصححة.

- **فشل في Batch 2 (إنشاء جداول):**
  - غالباً السبب: قيود موجودة مسبقاً بأسماء مختلفة أو trigger مكرر.
  - لا تُكمل حتى يصبح وضع الجداول الثلاثة واضحاً 100%.

- **فشل في Batch 3 (الدوال):**
  - تحقق من أنواع الأعمدة (`text/uuid/jsonb/integer`) وتطابقها مع الدوال.
  - لا تطبق Batch 4 قبل نجاح وجود كل RPC والدوال المساعدة.

- **فشل في Batch 4 (RLS):**
  - هذا أخطر جزء لأنه يؤثر على الوصول.
  - عند تضارب السياسات: ارجع للـBackup بدل ترك سياسات نصف مفعّلة.
